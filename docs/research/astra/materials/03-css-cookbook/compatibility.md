# Browser support, checked 2026-10-08

The table records **first unprefixed desktop support for the named primitive/syntax**, not the minimum browser for this complete demo site and not a promise of pixel identity. Compose a recipe by taking the newest requirement among its primitives; modern layout, modern colour syntax and the demo controls have their own requirements. The pages are intended for current browsers. Historic versions were not executed.

1. Safari's basic text-shadow entry begins at 1.1; its attached note says versions before 4 draw only the first shadow. The recipe uses a pair, so the table uses 4.
2. Safari 9–17.x needs `-webkit-backdrop-filter`; Safari 18 supports the unprefixed property. Include both declarations only when that older range is in scope. Filters need transmitted pixels to be visible; syntax support does not prove the intended backdrop was sampled.
3. BCD notes pre-123 Firefox could fail when the GPU vendor was unknown. This is a reason to retain the opaque fallback, not evidence that every Firefox 103 configuration works.
4. BCD starts `::before` at Firefox 1.5 but notes positioned pseudo-element bugs before 3.5; the positioned decoration recipe uses the conservative 3.5 floor. `content:""` and a supported host element are still needed.
5. BCD records partial relative-colour support in Chrome 119–121 and Safari 16.4–17.x. Chrome's early `rgb()` channel scaling and `oklch()` lightness scaling differ; Safari's early percentage/unit calculations are incomplete. The table uses full entries for these functions. `@supports` checks parsing, not these historic numeric bugs. Consult both the `rgb.relative_syntax` and `oklch.relative_syntax` records in the extract. Two-colour `color-mix` is separate from later variadic syntax, which these demos do not use.
6. BCD literally says `"preview"` for Safari and Firefox corner-shape. **No stable release number is asserted for either.** A numeric future key in a data source's version list does not establish a stable release or a tested implementation.

## Recipe-level support decisions

- T01 linear/radial and the multi-radial mesh approximation: C12/C13; conic adds C14. Optional explicit interpolation adds C20. A native editable mesh-gradient primitive was **not found** in the [MDN gradient reference](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/gradient) or the pinned gradient BCD file; the demo is explicitly an approximation.
- T02 shadows, recess, bevel and modeled depth: C01. Glyph-silhouette `drop-shadow()` uses C08; the filter acts on rendered alpha rather than a box and has no inset/spread argument. [MDN drop-shadow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/filter-function/drop-shadow), checked 2026-10-08.
- T03 inner/outer glow: C01; glowing text adds C02. T04 pseudo highlight: C11+C12/C13. T05 packaged SVG noise: C10; optional blend adds C18. T06 letterpress: C02.
- T07 double-background rounded edge: C03+C05+C12, hence primitive composition floor Chrome 26 / Safari 7 / Firefox 16. Standard masked gradient ring: C06+C12, hence Chrome 120 / Safari 15.4 / Firefox 53. Its solid border fallback uses C05. Border-image support (C04) does **not** mean border-radius clips that image.
- T08 frosted backdrop: C07, with an opaque fallback. T09 displacement on owned inline SVG: C09+C10. Arbitrary HTML backdrop refraction through `backdrop-filter:url(#filter)` is **unverified across all three engines** in this audit; do not infer it from these element support rows. The separate `filter.svg_elements` BCD subfeature concerns the **CSS property on SVG elements**, not SVG presentation-attribute filters; it even records Safari false. The inline SVG demo uses the presentation attribute, not that CSS-property path.
- T10 squircle: C17 over C05 fallback. T11 derivation: C15/C16 and, when consuming paired Area colors, C19; static semantic fallback comes first. T12 light direction: authored offsets/stops use the corresponding shadow/gradient rows; no browser feature simulates a complete lighting rig.
