# Treatments: preserve ink, then add decoration

**Status:** capability analysis and authored proposals. All aesthetic limits below are recommendations; no effect strength has been owner-approved. Evidence IDs resolve in [sources.md](sources.md).

## Use the same layer record as the rest of the series

For both `glyph` and `text`, retain `content.ink` as the semantic, readable foreground. Put relief in `content.decoration[]` referencing `shading.inset`, `shading.cast` and `reflection`; put glow in `emission`. Record `illumination` and an explicit glyph/letter alpha clip. A glyph printed on a raised button is still flush ink relative to that button unless an inscription recipe deliberately models it as recessed or raised. Parent elevation does not automatically give the glyph its own cast shadow. [R2, R3]

**Proposed record:** `{role, context, sourceGeometry, contentInk, decoration, light, relief, bounds, fallback}`. `context` includes functional/display, actual size, density, theme, background, state and preferences. `bounds` is effect extent, not a larger hit area or changed inset. Keep texture/backdrop acquisition off glyphs and letters by default; do not lens text simply because the host is glass. Functional parts receive **None**; a reviewed inscription may receive **Trace** (one dominant relief or emission cue). These are ordinal caps from task 05, not opacity percentages. [R2–R4]

## Capability matrix

“CSS only” means unchanged inline geometry and existing paint hooks. “Definitions/parts” changes rendering markup, not the drawing. “Filled” means a designed silhouette with preserved counters; Area may already derive it. [A1–A5; S1–S5]

| Treatment | Layer stack and depth | Unchanged stroked SVG | When filled/extra parts are needed | Type and 12–16px consequence |
| --- | --- | --- | --- | --- |
| Engraved glyph | Readable dark/semantic ink, shadowed inner lip and lit lower rim under a top light; recessed relief, flush layout | CSS `drop-shadow()` below the alpha gives a shallow engraved **suggestion**. An actual inner lip needs an SVG alpha-composite filter; `drop-shadow(inset …)` is invalid | No filled variant for a line incision. A broad carved cavity with separate floor/wall needs a closed silhouette and clipped shading | Relief must not replace the core. A one-pixel echo is comparable to the small stroke; tight gaps can become doubled or bridged |
| Embossed glyph | Core ink, upper light rim, lower cast/shaded lip; raised relief | An upper light shadow plus lower dark shadow suggests relief without moving paths. An independent SVG filter graph avoids shadows of prior shadows | Broad bevels, specular faces or extrusion need a filled body; a thin line has little interior area | Bright same-surface ink that relies on relief alone is unsuitable for required small marks. Do not simulate weight by adding an all-around outline |
| Glowing glyph | Opaque readable emitter plus a separate outer emission lobe; normally flush | CSS zero-offset `drop-shadow()` follows the stroked alpha. Preserve the original source; do not `blur()` the whole icon | No filled variant required. A broad luminous panel/face uses a filled shape; that is a different receiver from a stroked symbol | Bloom spreads across counters and adjacent letters; bright emission on dark is still decoration, not a readable core or sole selected/focus cue |
| Duotone glyph | Two semantic ink regions, or one primary ink and subordinate body tint; no implied depth | Possible when distinct shapes already exist and have stable semantic selectors. CSS alone cannot discover “body”, “detail” or which subpath means what | Named parts/masks usually required; a tinted body behind dark outlines needs a closed body. Existing `data-filled` roles describe geometry generation, not a public duotone API | Never fade the required mark to make hierarchy. Test each necessary region against what touches it; two hues do not guarantee separation |
| Gradient glyph | Gradient replaces the ink paint over the existing stroke/solid; optional reflection only if independently declared | SVG `stroke: url(#id) currentColor` works without redrawing when a paint server exists. CSS `linear-gradient()` is not an SVG stroke paint server | A `<linearGradient>` definition and stable targeted ink selectors. No filled variant needed for a gradient line. A broad gloss band or body gradient needs filled area | Narrow strokes sample few pixels across their width. Smooth transitions across the whole icon are more coherent than separate gradients per path. Avoid bright/dark bands that erase parts |
| Letterpress text | Real font ink with a restrained lower highlight (optionally upper inner lip); recessed inscription | `text-shadow` is CSS only for text; it does not paint path geometry | No conversion to outlines needed. True inset text shading needs an explicit text-alpha filter/mask, not box-shadow | Reversed relief becomes embossing. Keep actual selectable text and readable ink; duplicate edge images compete with punctuation and narrow stems |
| Glowing text | Real font ink plus outer emission shadows; flush luminous inscription | `text-shadow` is the natural text operation; several independent shadows can leave core text intact | No filled icon variant; the font already supplies glyph outlines. Do not replace text with images to obtain the glow | Reserve for sparse display text. Body copy, code, numerical input, placeholders and status labels remain plain. Core needs contrast even where the halo is clipped |

The mechanisms are supported by S1–S5; relief direction and usage limits are proposed art direction. Under light from above, raised relief puts the highlight above and shade below; incised relief reverses the edge cues. Reversing a shadow is an illusion of depth, not a reconstructed physical cavity.

## What the current renderers permit

**Inline package `Glyph`.** Parent CSS can set currentColor and target the exposed `data-area-glyph` SVG; CSS selectors can override child presentation attributes. Setting `stroke` only on the root is insufficient when each path declares its own stroke. Never blanket-select all `path` elements: More is fill-only; Stop uses fill plus stroke. `Glyph` currently accepts neither arbitrary children nor a paint/part prop, so scoped gradient definitions need a wrapper/renderer extension proposal. Its path array also loses source-level semantic role annotations. [A1]

**Docs pilot.** Generated outline SVGs preserve paths, rects and circles; filled SVGs can contain masks and separate body geometry. The prototype can reuse these without redrawing. However, CSS such as `svg * { fill: … }` also recolors mask black/white and destroys holes. Select visible ink outside definitions and leave luminance masks alone. Per-instance IDs must be unique; Area already uses React `useId` for masks. Put new paint definitions in the same instance/scope so stop colors derive from that theme, not a global defs node with another theme's values. [A2, A3; S3]

**Embedded assets.** These conclusions concern inline SVG. An SVG used as an external image does not expose its internal path selectors to host CSS. A filter on the image can affect the whole alpha result; it cannot assign semantic colors to its hidden parts. A CSS mask can paint a silhouette, but loses independent part colors. Keep photographs, brand artwork and emoji out of automatic material recoloring. This is a rendering-boundary inference from the inline paint model and image restrictions, not a tested asset import feature in Area. [S1, S3, S9; R3]

## Recipes and pitfalls

The runnable lab records all literal experiment values in [lab.css](lab.css) and [lab.js](lab.js). They are authored demonstrations, not measurements of the owner's board.

### Relief and glow

On inline SVG, `filter: drop-shadow(0 1px 0 var(--inscription-light))` adds an alpha-shaped lower highlight. A second negative offset can suggest an upper shadow, but filter functions run sequentially: the next lobe also sees the previous one. An independent multi-lobe SVG graph starts each branch from `SourceAlpha`, colors it with `feFlood`/`feComposite`, then merges branches with `SourceGraphic`. `box-shadow` shadows the SVG's rectangular box, not its path silhouette; inset box-shadow creates a recessed box, not engraved glyphs. [S1, S4]

For actual inward shading, compute `A out offset(A)` from `SourceAlpha` for each direction, tint the resulting edge mask, clip it back to A and composite it over the core. Sign determines the lit/shaded edge. Blur only the edge mask if needed. This avoids redrawing, but a subpixel-width stroke can be mostly edge, so capability does not make it a good small-size treatment. Declare filter/primitive units, filter region, interpolation space and overflow intentionally; confirm ancestor clips and neighboring ink. SVG specular lighting can use alpha as a height field, but it is not knowledge of the object's true surface. No lighting-filter or true-inset rendering is claimed as tested by this lab. [S4]

Text shadows have no inset or spread parameter and do not follow the CSS box. A negative-y light plus positive-y shade suggests embossed type; reverse them for letterpress. Keep the font weight, tracking, line height and foreground fixed. A material must not “repair” blurred type with extra font smoothing, transformed text or heavier weight. [S2; A2, A5]

### Gradient ink

Use an instance-local `<linearGradient gradientUnits="userSpaceOnUse" x1="0" y1="0" x2="16" y2="16">` for a 16-unit drawing. Colors and direction in the lab are authored; 16 is the actual drawing coordinate extent. User-space coordinates give every part one coherent gradient and work for straight horizontal/vertical paths whose geometric bounding box has zero height/width. Keep `fill="none"` on open lines; only visible filled dots receive a fill gradient. `url(#id) currentColor` supplies a paint fallback if the server is unavailable. A per-instance React ID avoids collisions, but resolving scope/IDs is a renderer change, not a color token alone. [A1–A3; S3]

Text uses a CSS gradient clipped to text with an opaque fallback color. Apply transparent text only inside a supported enhancement, set a solid background-color under the gradient for image failure, and explicitly restore real text color/background under forced colors. Limit clipping to the text span: using `color: transparent` on a parent also makes currentColor icons transparent. Avoid `-webkit-text-fill-color: transparent` unless it is reset in every fallback. The lab uses no prefixed text fill. [S5, S7]

All gradient positions, not only the stops, need adequate contrast over all permitted backdrops. An intermediate luminance or alpha mix can be the worst case; a dark-to-light gradient may disappear somewhere even when its endpoints separately work on different grounds. Choose a light-theme and dark-theme paint set from tested ink ranges, or fall back to flat ink. Do not change gradient stops on hover when that changes the foreground. [A6; S6; R3]

### True duotone and broad materials

An existing Calendar can separate dates from frame with research-only annotations; that is the lab's duotone demonstration. Exporting that as a library-wide feature needs named roles, e.g. `body`, `mark`, `secondary-outline`, and per-icon review. `nth-child` is not a semantic contract. Some source paths contain several subpaths; independently tinting them needs path decomposition or masks even though coordinates can remain unchanged. Apple's annotated rendering modes offer a useful precedent, not a shortcut around this authoring work. [A3; S8]

Use existing filled variants when the intended effect needs a broad face: metal bevel, jelly body, internal gradient/gloss, frosted body or substantial inner shadow. Calendar already supplies body/counters; Search intentionally stays an open lens with a heavier line. Filling its closed lens makes a different picture. Do not add `fill: currentColor` to every stroke, close open outlines arbitrarily, or remove negative-space masks. If no valid filled body exists, the options are a separately reviewed semantic body variant or keeping the outline treatment. Text is already filled font geometry and needs no custom outline export. [A3, A5]

## Fit Area without changing its ownership

Proposed material recipe fields supply decoration, not a second typography or state system. Retain `--area-weight-icon`, the generated size factor, the font ramp and the existing semantic foreground. Derive any light/shade/emission colors from the resolved local foreground and surface at the same scoped emission boundaries used by the material proposal; do not register those derived paired colors with `@property`. New names such as `--area-material-glyph-glow-*` would be proposals, not current tokens. Surface still owns component elevation; a local inscription relief belongs to content decoration and must not add a second surface shadow. [R1–R4; A2, A6]

Use separate role overrides for `text` and `glyph`, and a context opt-in for display inscriptions. Reset optional effects at nested component/role boundaries. A parent glow must not filter the entire Button/Menu label-and-icon group, because that also changes core text and icon compositing. Hover foreground stays fixed; selected/invalid meaning and keyboard focus remain independent. Never apply duotone to a status mark merely to match the material palette. [A6; R3]
