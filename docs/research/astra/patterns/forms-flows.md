# Forms and multi-step flows

Checked 2026-09-28. [Method, status meanings and priorities](README.md).

These are proposed Area recipes informed by the cited public examples and guidance. Anatomy is the proposed reading order; variations are candidates to offer, not a claim that every source implements them. Responsive behavior is an Area recommendation unless a source observation explicitly says otherwise. No dimensions are inferred from images.

Component availability is pinned to `18b86465d542f620d532fee351c4f28d50c8ac3a`. `recipe` means reusable packaging is absent but the baseline is composable; `partial` and `missing` identify additional shared behavior or adapters. Native headings, paragraphs, links, lists, forms and layout CSS remain valid building blocks.

## Create or edit resource form

**Purpose.** Collect related information and make submission outcomes understandable.

**Anatomy, in order (proposal).**

1. Task title and context
2. Error summary when needed
3. Grouped labeled fields
4. Optional scheduling section
5. Primary and cancel actions
6. Submission result

**Common variations to catalogue.**

- Single column.
- Sectioned form.
- Inline editor in a detail page.

**Extra requirements for expanded variants.**

- DatePicker — **partial**. Calendar is built. A composed date-entry and popup contract, including segmented input, is not found. [range cross-check](https://github.com/ethanwongwork/area/blob/7435813c947188664c665dc59f5fa0ffc5de4e8c/docs/research/library-range/date-picker.md#L198).

**Responsive proposal.** Stack columns into the same reading order as labels and errors; avoid changing keyboard order to match a decorative grid. General layout basis: [Fluent — Layout](https://fluent2.microsoft.design/layout).

**Behavior boundary.** Calendar can be used inline; it does not supply segmented date entry. Form aggregation, dirty-state protection and server errors need a shared contract.

**Source observations.**

- [GOV.UK — Recover from validation errors](https://design-system.service.gov.uk/patterns/validation/) (guidance; checked 2026-09-28). Retain entered answers; link a focused error summary to errors at fields; distinguish invalid input from service or permission problems.

## Multi-step question flow

**Purpose.** Break a longer task into focused questions with a clear way back.

**Anatomy, in order (proposal).**

1. Task context and back link
2. Progress or step label
3. Current question and help
4. Answer fields
5. Continue or save-for-later

## Review and submit

**Purpose.** Let people check accumulated answers before committing the task.

**Anatomy, in order (proposal).**

1. Review heading
2. Grouped answers and change actions
3. Consequences or declaration
4. Submit action
5. Completion reference and next steps

**What Area lacks for this baseline.** Form validation and error summary. Existing controls cover only the reuses listed above.

**Common variations to catalogue.**

- Summary rows.
- Section review cards.
- Review followed by a separate confirmation page.

**Responsive proposal.** Stack answer values beneath their labels; keep each change action associated with the exact answer it changes. General layout basis: [Fluent — Layout](https://fluent2.microsoft.design/layout).

**Behavior boundary.** Change links return to populated steps. Submission must avoid accidental duplicates; a success panel is shown only after the app reports success.

- [GOV.UK — Confirmation pages](https://design-system.service.gov.uk/patterns/confirmation-pages/) (guidance; checked 2026-09-28). Confirm completion and explain what happens next.
