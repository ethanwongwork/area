## 1. shadcn/ui registry + CLI

**Generated vs owned.** Code is copied into the user's tree and then owned by them; there is no lock file, no record of what was installed or at which version. Placement comes from `components.json` `aliases` (`utils`, `components`, `ui`, `lib`, `hooks`) and per-file `target`.

**registry.json** (`$schema: https://ui.shadcn.com/schema/registry.json`): `name`, `homepage`, `items[]` (each a registry item). `shadcn build` writes per-item JSON (default `--output ./public/r`). Source: https://ui.shadcn.com/docs/registry/registry-json

**registry-item.json** (`$schema: https://ui.shadcn.com/schema/registry-item.json`): `name`, `title`, `description`, `type` (`registry:base|block|component|font|lib|hook|ui|page|file|style|theme|item`), `author`, `files[]` {`path`, `type`, `target` — required for `registry:page`/`registry:file`, supports `@ui/`, `@components/`, `@lib/`, `@hooks/`, `~` root}, `dependencies`, `devDependencies`, `registryDependencies` (names, `@namespace/item`, URLs, local paths), `cssVars` {`theme`, `light`, `dark`}, `css` (`@layer base`, `@utility`, `@keyframes`, `@plugin`), `envVars` (merged into `.env.local`, existing vars not overwritten), `tailwind` (deprecated; use `cssVars.theme` for v4), `font`, `docs`, `categories`, `meta`. Source: https://ui.shadcn.com/docs/registry/registry-item-json

**components.json**: `$schema`, `style` (`new-york`; `default` deprecated), `rsc`, `tsx`, `tailwind` {`config` (blank for v4), `css`, `baseColor`, `cssVariables`, `prefix`}, `aliases`, `iconLibrary`, `registries` (`"@acme": "https://…/{name}.json"` or `{url, headers, params}` with `${ENV}` expansion). `style`, `baseColor`, `cssVariables` cannot change after init. Source: https://ui.shadcn.com/docs/components-json

**Update / overwrite behaviour (from source, `packages/registry/src/updaters/update-files.ts`).** For each file: if it exists and content is the same after import rewriting (`isContentSame`), it is skipped. If it exists and differs and `--overwrite` is not set: non-interactive runs skip it; interactive runs prompt `The file X already exists. Would you like to overwrite?` (default **No**). Summary line: `Skipped N files: (files might be identical, use --overwrite to overwrite)`. `.env` files are merged, not replaced. So the only modes are skip, or whole-file overwrite: **no merge, no base version**. Source: https://github.com/shadcn-ui/ui/blob/main/packages/registry/src/updaters/update-files.ts

**Diff.** `shadcn diff` still exists but is marked `[DEPRECATED] Use add [component] --diff instead.` (line diff of local vs registry, via `diffLines`). `add` flags: `--yes`, `--overwrite`, `--all`, `--path`, `--dry-run`, `--diff [path]`, `--view [path]`. Other commands: `init`, `apply` (presets, `--only theme|font`), `view`, `search`/`list`, `build`, `docs`, `info`, `migrate` (`cn`, `icons`, `base-color`, `radix`, `rtl`), `eject`, `registry add|build|mcp|validate`. Sources: https://ui.shadcn.com/docs/cli ; https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/commands/diff.ts

**Determinism.** Output is transformed per project (`transformImport`, `transformRsc`, `transformTwPrefixes`, `transformCssVars`, `transformIcons`, `transformRtl`…), so "same registry item" yields different bytes per config; comparisons normalize imports.

**MCP server** (`npx shadcn@latest mcp`; `shadcn mcp init --client claude`). Server `shadcn` 1.0.0, 7 tools: `get_project_registries`, `list_items_in_registries` {registries?, types?, limit?, offset?}, `search_items_in_registries` {query, …}, `view_items_in_registries` {items: ["@shadcn/button"]}, `get_item_examples_from_registries` {query}, `get_add_command_for_items` {items} (returns the CLI command; the agent runs it), `get_audit_checklist` (post-install checklist: imports, deps, lint, types, browser). It is read/plan-only; writes go through the CLI. Sources: https://ui.shadcn.com/docs/mcp ; https://github.com/shadcn-ui/ui/blob/main/packages/shadcn/src/mcp/index.ts

## 2. Style Dictionary and DTCG

**DTCG status.** Design Tokens Format Module **2025.10**, "Final Community Group Report", 28 Oct 2025, described as stable ("first stable version") but not on the W3C Standards Track. Three modules: Format, Color, Resolver; tools may cite `2025.10` as conformance version. Sources: https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/ ; https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/ ; https://www.designtokens.org/tr/2025.10/

**Format.** A token is any object with `$value`. Optional `$type`, `$description`, `$extensions` (reverse-domain keys; tools MUST preserve unknown extension data), `$deprecated` (bool or string). Types: `color`, `dimension`, `fontFamily`, `fontWeight`, `duration`, `cubicBezier`, `number`, `strokeStyle`, `border`, `transition`, `shadow`, `gradient`, `typography`. `$type` inherits from the nearest group; tools MUST NOT guess type from value. Groups: objects without `$value`; `$extends: "{button}"` (group inheritance, local overrides replace whole tokens); `$root` reserved name for a group's base token. Aliases: `"{group.token}"` (whole token) and JSON Pointer `{"$ref": "#/colors/blue/$value/components/0"}`; circular refs are errors. Names may not start with `$` or contain `{`, `}`, `.`. Files: `.tokens` or `.tokens.json`, media type `application/design-tokens+json`. Dimension values are objects (`{"value": 0.1, "unit": "px"}` in the spec's examples). Source: format URL above.

**Color module.** `$value: {colorSpace, components, alpha?, hex?}`; `colorSpace` ∈ `srgb, srgb-linear, hsl, hwb, lab, lch, oklab, oklch, display-p3, a98-rgb, prophoto-rgb, rec2020, xyz-d65, xyz-d50`. Source: https://www.designtokens.org/tr/2025.10/color/

**Resolver module (themes/modes).** Document: `version` (MUST be `2025.10` per the 2025.10 TR page; the CG-FINAL page text inconsistently says `2025-10-01`/`2025-11-01`), optional `name`, `description`, `$schema` (https://www.designtokens.org/schemas/2025.10/resolver.json), `sets` {name: {sources: [inline | {$ref}]}}, `modifiers` {name: {contexts: {ctx: [sources]}, default?}}, `resolutionOrder: [{$ref:"#/sets/base"}, {$ref:"#/modifiers/theme"}]`. Input `{"theme":"dark"}` picks a context per modifier; later sources win; aliases resolve after flattening. Modifiers need ≥2 contexts. Sources: https://www.designtokens.org/tr/2025.10/resolver/ ; https://www.w3.org/community/reports/design-tokens/CG-FINAL-resolver-20251028/

**Style Dictionary.** First-class DTCG since v4; 2025.10 support is "a work in progress in v5". Config: `source`, `include`, `tokens`, `platforms` {`transformGroup`/`transforms`, `buildPath`, `prefix`, `files[]` {`destination`, `format`, `filter`, `options` {`outputReferences`, `showFileHeader`, `fileHeader`}}, `actions`}, `hooks`, `log`, `usesDtcg` (auto-detected), `expand`. **Determinism:** the header timestamp was made opt-in "to avoid redundant git diffs in CI" (`options.formatting.fileHeaderTimestamp: true` to restore). Output is generated, overwritten every build; no merge concept. Sources: https://styledictionary.com/info/dtcg/ ; https://styledictionary.com/reference/config/ ; https://styledictionary.com/reference/utils/format-helpers/

## 3. Tokens Studio Git sync

GitHub provider fields: name, PAT, `owner/repo`, branch, file **or folder** path, optional base URL (enterprise). Single file = all sets in one JSON (themes as root keys); multi-file (Pro) = one JSON per token set plus plugin data files: `$themes.json` (each theme `name`, `group`, `selectedTokenSets` {set: `enabled`|`source`|`disabled`}) and `$metadata.json` (`tokenSetOrder`). Push requires a commit message; Diff tab shows additions/removals; plugin can offer to open a PR. Pull **replaces** local tokens ("You will lose all Tokens in the plugin, and they can not be recovered!"). Branch switching (Pro) creates a branch from "Current changes" and opens Push; switching opens Pull to replace. **No merge or conflict resolution**; push/pull indicators only, and "Git sync enhancements – push, pull, merge, branching" is still a feature request. Sources: https://docs.tokens.studio/token-storage/remote/sync-git-github ; https://docs.tokens.studio/token-storage/remote-push-pull-changes ; https://docs.tokens.studio/token-storage/remote-branch-switch ; https://github.com/tokens-studio/sd-transforms (permutateThemes / `$themes` reading) ; https://feedback.tokens.studio/p/git-sync-enhancements

## 5. Panda CSS and Tailwind v4

## 8. Generators that update owned code

**Copier** (the closest model). Answers file `_answers_file` (default `.copier-answers.yml`), rendered from `{{ _copier_answers|to_nice_yaml }}` under the header `# Changes here will be overwritten by Copier; NEVER EDIT MANUALLY`; stores `_commit` (template git tag/ref, e.g. `v1.0.0`) and `_src_path` (template URL) first, then answers. Requirements: valid answers file, template versioned in git with tags (PEP 440 ordering), destination in git, clean `git status`. **Algorithm (`_apply_update` in `copier/_main.py`):** (1) render the *old* template version (`vcs_ref=_commit`, last answers, defaults) into temp `old_copy`, init a git repo; (2) run pre-migrations; (3) `git write-tree` of the real project; record files the user deleted (`diff-tree --diff-filter=D`, excluding `_skip_if_exists`) so they are not recreated; (4) render the *new* version directly over the project; (5) render the new version into temp `new_copy`; (6) compute the user's own edits as `git diff-tree --unified=<context_lines> HEAD(old_copy) <project tree>` (excluding answers file and `skip_if_exists` matches); (7) re-apply that diff on top with `git apply --reject`; (8) with `--conflict inline` (default) every `.rej` file is resolved by a real three-way `git merge-file -L "before updating" -L "last update" -L "after updating" <file> old_copy/<file> new_copy/<file>`, conflicted paths get index stages 1/2/3 written via `git update-index --index-info` so editors and `git status` show them as unmerged; `--conflict rej` leaves `.rej` files; (9) delete files the new template removed; post-migrations; tasks. Flags: `--defaults`, `--data k=v`, `--data-file`, `--vcs-ref=HEAD|:current:`, `--skip-answered`, `--conflict inline|rej`, `--context-lines`. `copier recopy` = fresh render with last answers, discards smart merge. `copier check-update --output-format json` → `update_available`, `current_version`, `latest_version`; `--quiet` exit 2 when available. `_skip_if_exists` files always exist but are never overwritten; `_exclude`, `_migrations` (update only), `_tasks`, `_min_copier_version`. Sources: https://copier.readthedocs.io/en/stable/updating/ ; https://copier.readthedocs.io/en/stable/configuring/ ; https://github.com/copier-org/copier/blob/master/copier/_main.py

**Cruft** (Cookiecutter). `.cruft.json`: `template`, `commit`, `checkout`, `context` (answers), `directory`, `skip` (globs never updated). `cruft create|link|check` (exit 1 when behind, for CI)|`diff --exit-code`|`update`. Update renders template at old `commit` and at latest, diffs the two renders (template-side change), applies it to the project with `git apply -3`, falling back to `git apply --reject` (`.rej`) on failure; requires a clean tree; `--skip-apply-ask`, `--allow-untracked-files`, `--variables-to-update '{…}'`. Then writes the new `commit`. Sources: https://cruft.github.io/cruft/ ; https://github.com/cruft/cruft/blob/master/cruft/_commands/update.py

**Yeoman**: writes staged in mem-fs; "every write happening on a pre-existing file will go through a conflict resolution process" (interactive per-file overwrite prompt); `.yo-rc.json` marks project root/config. No base version, no merge. https://yeoman.io/authoring/file-system

**Projen**: opposite model, generated files are not user-owned. Marker `~~ Generated by projen`, files read-only by default, committed by default with `.gitattributes` `linguist-generated` and an anti-tamper CI check; `.projen/files.json` manifest lets synth delete orphaned generated files. Customisation only via `.projenrc` (escape hatches/overrides). Sources: https://github.com/projen/projen/blob/main/src/common.ts ; https://github.com/projen/projen/blob/main/src/file.ts ; https://github.com/projen/projen/blob/main/src/cleanup.ts

**Angular `ng update`**: bumps packages and runs codemod migrations (schematics); `--migrate-only --from --to --name`, `--create-commits`/`-C`, `--allow-dirty` (default false). Edits by AST transform rather than template diff. https://angular.dev/cli/update

**Rails `bin/rails app:update`**: per-file prompt `Overwrite …? [Ynaqdh]`, diff/merge tools from `THOR_DIFF`/`THOR_MERGE`; new behaviour quarantined in `config/initializers/new_framework_defaults_X_Y.rb` to opt into gradually. https://guides.rubyonrails.org/upgrading_ruby_on_rails.html

## 9. MCP: tool shape and stdio

**Versions.** Schema dirs: `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, **`2026-07-28`** (current "latest"), `draft`. But the official TypeScript SDK (npm 1.32.2) still has `LATEST_PROTOCOL_VERSION = '2025-11-25'`, `SUPPORTED_PROTOCOL_VERSIONS = ['2025-11-25','2025-06-18','2025-03-26','2024-11-05','2024-10-07']`: clients in the field mostly still speak the **legacy** handshake. Sources: https://modelcontextprotocol.io/specification/latest ; https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/schema ; https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/core/src/constants.ts

**stdio framing (both eras).** Client spawns server; server reads JSON-RPC 2.0 from stdin, writes to stdout; one message per line, "MUST NOT contain embedded newlines"; stdout carries only MCP messages; logs go to stderr; server should exit on stdin EOF. Request ids are string|number, never null. https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio

**Legacy (2025-11-25) handshake.** Client → `{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{…},"clientInfo":{"name":…,"version":…}}}`; server → `{"result":{"protocolVersion":"2025-11-25","capabilities":{"tools":{"listChanged":false}},"serverInfo":{"name","version"},"instructions":"…"}}` (echo the client's version if supported, else the latest the server supports); client → notification `notifications/initialized` (no id, no reply). Then `tools/list` → `{"tools":[…],"nextCursor"?}`; `tools/call` {`name`,`arguments`} → `{"content":[{"type":"text","text":"…"}],"structuredContent"?:…,"isError"?:bool}`. Also answer `ping` with `{}`. Unknown method → `-32601`; unknown tool/bad params → `-32602`. https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle

**Modern (2026-07-28) changes.** No handshake; stateless. Every request carries `params._meta["io.modelcontextprotocol/protocolVersion"]` (required), `…/clientCapabilities` (required), `…/clientInfo` (optional); missing required fields → `-32602`. Servers MUST implement `server/discover` → `{resultType:"complete", supportedVersions:["2026-07-28"], capabilities:{tools:{}}, _meta:{"io.modelcontextprotocol/serverInfo":{name,version}}, instructions?, ttlMs?, cacheScope?}`. Every result MUST include `resultType` (`"complete"` or `"input_required"`; clients treat absent as complete). Unsupported version → error `-32022` with `data:{supported:[…], requested}`. Servers never send requests (elicitation etc. via `InputRequiredResult`). A dual-era server picks legacy semantics when the first message is `initialize`, modern when a request carries `_meta` protocolVersion; modern-only servers should name supported versions in their `initialize` error. Sources: https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning ; https://modelcontextprotocol.io/specification/2026-07-28/basic/index ; https://modelcontextprotocol.io/specification/2026-07-28/server/discover

**Tool definition.** `name` (1–128 chars, `[A-Za-z0-9_.-]`, case-sensitive), `title?`, `description`, `inputSchema` (JSON Schema object, default dialect 2020-12, never null; no-arg tools `{"type":"object","additionalProperties":false}`), `outputSchema?` (if set, server MUST return conforming `structuredContent`, and SHOULD also return the JSON serialized in a text block), `annotations?` (untrusted hints), `icons?`. Return tools in deterministic order. Tool failures the model can fix → `isError: true` result, not a JSON-RPC error. https://modelcontextprotocol.io/specification/2026-07-28/server/tools
