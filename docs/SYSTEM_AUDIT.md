# Area — system audit and completion plan

**Audit date:** 2026-09-14. **Baseline:** `e07ec11`, followed by the requested 75/100/150 stroke trial.
**Status:** Research and recommendations; the roadmap is not implemented. The stroke trial is implemented and visible locally, with an intentionally unreconciled contrast gate. No thresholds or waivers were relaxed.

## Conclusion

Area has a strong visual foundation and a useful organizing concept: a restrained interface whose appearance is composed from independent choices. Keep the eight-axis model, semantic tokens, framework-free CSS, generated demonstrations, and the separation between meaning (tone) and emphasis (variant).

Area is currently a **visual system and presentational component kit**, with native behavior on native controls. It is not yet a release-ready, accessible React component library. The most valuable next work is to make its existing promises reliable: nested theming, real interaction, rendered-state contrast, preference handling, public APIs, and reproducible release checks. More palette colors or radius stops will not close those gaps.

**Priority order:**

1. Repair contrast coverage and nested theme resolution.
2. Complete keyboard/focus behavior and form semantics on existing components.
3. Finish motion, typography scoping, compact targets, and forced-color support.
4. Prove installation, browser compatibility, and API/documentation parity.
5. Add validated customization profiles and only then expand the component catalog.

The full sequence, acceptance conditions, and effort bands are in [ROADMAP.md](ROADMAP.md). “Complete” means a dependable first release for web application interfaces, not every possible widget or visual style.

## What was examined

Source review covered token generation and semantic resolution, all eight axis definitions, the CSS emitter and registry checks, component styles, all React component source files, the manifest/helper boundary, package manifests, docs generation and inspector behavior, existing tests, and maintenance guidance.

Browser checks covered the default light page and dark switch, actual Select/segmented stroke colors, nested color scopes, explicit motion-none, an elevated outline button, and the Tabs keyboard example. These were sampled checks in the in-app Chromium browser, not a full browser or assistive-technology certification. Mobile reflow, Windows forced colors, VoiceOver/NVDA, and the complete interaction matrix still need dedicated verification.

Reproducible evidence:

- [Measurements](research/2026-09-14/measurements.json), generated by [measure.ts](research/2026-09-14/measure.ts).
- [Unmodified contrast report](research/2026-09-14/contrast.txt).
- [Scope probe](research/2026-09-14/scope.html) and [browser observations](research/2026-09-14/browser-observations.md).
- Run `node docs/research/2026-09-14/measure.ts` for fresh token measurements. The saved JSON is a dated snapshot, not a continuously updated status file.

The registry contains 2 theme × 3 neutral × 11 brand × 4 type × 2 density × 8 radius × 4 surface × 3 motion choices: **50,688 preset combinations**. Color tests cover **66 resolved color themes**. Namespace ownership reduces collision testing; it does not prove all those rendered combinations work. The scope bugs below demonstrate why composition checks remain necessary.

Verification after the trial:

- **8,810 passing / 165 failing tests**, 8,975 total, six files; all 165 failures are the five stroke assertions across 33 light color themes.
- Contrast report: **173 passing assertion groups, five failing, four waived**, across 66 themes.
- Package/docs build, typecheck, and manifest parity pass. Docs build: 38 pages, 64 demos; dogfood audit: 36/36 manifest components represented.
- Build success does not imply test success. The contrast report itself prints failures but exits successfully; use `npm test` as the blocking command.
- A direct root import of `@area/tokens` fails with `ERR_MODULE_NOT_FOUND`.

The test count mostly reflects parameterized color checks. It is not evidence of thousands of UI behavior tests: all six test files are in the token package.

## Stroke trial

The requested hierarchy is now global through `INVERSION` in [curves.ts](../packages/tokens/src/color/curves.ts):

- **Decorative, 75:** `border-decorative`, `#f3f3f3` in the default light neutral. Panel/card/table/code framing and dividers. Approximately **1.110:1** against white.
- **Faint, 100:** `border-faint`, `#eeeeee`. Menu/Popover frames, token badges, and segmented tracks. Approximately **1.160:1** against white.
- **Subtle, 150:** `border-subtle`, `#e2e2e2`. Input, Select, Textarea, unselected Chip, neutral outline Button, and selected segmented items. Approximately **1.295:1** against white.

Cool and warm casts use their own corresponding rungs. Dark remains decorative 800 (`#282828`) and faint/subtle 750 (`#333333`) in the default neutral. Hover and focus were not changed. The native Select's popup remains platform-owned; Area controls its closed field, while Menu/Popover are Area surfaces. There is no separate Combobox.

**Visual judgment:** the hierarchy is coherent and very quiet. Large container seams recede appropriately. The segmented track is the weakest distinction: its faint stroke reaches a worst case of **1.063:1 against its own subtle fill**. A shadow can make an edge look stronger than its nominal border, so compare the flat surface preset as well as outlined.

**Gate impact:** subtle-on-page/surface falls below 1.3; faint-on-page/surface below 1.2; faint-on-subtle below 1.1. Each fails in all 33 light themes. Decorative 75 still passes its existing 1.1 floor. These are Area's aesthetic floors, not general WCAG thresholds.

**Recommendation for the next decision:** keep 75 as the candidate decorative level. For the existing gate, 150 for faint and 200 for subtle provide a straightforward recovery; the prior 100/150/200 hierarchy also passed. This audit leaves the exact requested 75/100/150 trial visible so it can be judged. Do not ship it as a green state or round 1.295 up to a 1.3 pass.

A pale decorative rule is not inherently an accessibility failure. A boundary or state marker that is required to identify a control is a different job: assess the actual control, label, fill, and adjacent colors. W3C gives both exempt button-boundary examples and input/checkbox examples where the indicator must meet 3:1. A single blanket exemption for all resting controls is not defensible. [S1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## Findings

Priority meanings: **P0** blocks a release claim; **P1** belongs in the first usable release; **P2** improves the system after those contracts are established. These are recommendations, not estimates of exploit severity.

### F01 · P0 · Nested color scopes do not compose

**Verified in-browser.** [emit/css.ts](../packages/tokens/src/emit/css.ts), `presetSelector()` and `emitAxes()`, only emit dark neutral/brand overrides when theme and color selection appear on the same element. The dark theme also injects default brand/neutral values, while the light theme does not equivalently reset them.

- Dark parent + child `data-area-neutral="warm"`: child page token becomes white and foreground `#2b2722`; explicit dark+warm reference resolves to page `#16120d`, foreground `#f1eeeb`.
- Dark parent + green-brand child: brand surface becomes light `#f1fbf5`; explicit dark+green reference is `#003d24`. Solid happened to match, so checking only the solid color would miss the bug.
- Light child in dark parent: page remains `#121212`, foreground `#eeeeee`, and native `color-scheme` remains dark.

**Next:** define closest-scope inheritance precisely, including a theme-only child inside a non-default brand/neutral parent. Resolve polarity and role choice together at the scope boundary. Do not solve this solely by adding descendant selectors: an outer dark ancestor can then override an inner light island. A scope provider that materializes the effective selection is a viable React approach; the CSS-only contract must be equally explicit.

**Done when:** dark/light islands and independently nested brand/neutral choices match `resolveTheme()` at two or more nesting levels; native controls agree; portal overlays retain the trigger's effective theme.

### F02 · P0 · The contrast contract understates ordinary text requirements

[contrast/assertions.ts](../packages/tokens/src/contrast/assertions.ts) tests placeholders at 3:1 and solid hover labels at `WCAG.LARGE_TEXT` (3:1), although Area's common controls render 11–16px text at weight 400/500. Placeholders and hover text are covered by text contrast requirements; normal text requires 4.5:1, with the large-text exception depending on actual size/weight. [S2](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

Independent diagnostics against 4.5:1 found:

- Placeholder on `bg-surface`: **44/66** color themes fail; worst **3.717:1**.
- Brand solid hover: **24/66** fail; worst **3.743:1**.
- Danger, success, info, discovery solid hover: **33/66 each** fail; worst ratios respectively **4.002, 3.743, 4.203, 4.114**.
- Warning and caution hover pairings pass this diagnostic.

These predate the stroke trial. Four syntax-color assertion groups are already waived; their worst case is about 2.80:1. Keep their history visible, but resolve them before a general accessible-release claim. A waiver records a decision; it does not make a failing presentation conformant.

**Next:** map actual text roles and rendered states to thresholds, including normal-size hover labels, placeholder text, selected/active states and translucent surfaces. Choose readable semantic steps without changing the vendored palette. Keep APCA as a separately named supplementary policy; it is not a replacement for the applicable WCAG 2.2 checks.

### F03 · P0 · Focus checks measure a different color from the painted ring

[emit/base.ts](../packages/tokens/src/emit/base.ts) constructs `--area-ring` from `border-focus` at **45% opacity**. Button and Segmented remove the outline and use that shadow. The contrast assertion tests the opaque token instead of the composited ring. Default light indigo focus token `#3c2ebe`, composited at 45% over white, measures approximately **2.376:1**. Inputs additionally change their actual border, so evaluate each component rather than applying one verdict to all of them.

No forced-colors rules were found in the system CSS. CSS forced-color processing removes box shadows; a focus indicator built only from a shadow is therefore at risk of disappearing. [S3](https://www.w3.org/TR/css-color-adjust-1/)

**Next:** provide a reliable visible focus indicator, measure its painted composite and all adjacent surfaces, add a system-color outline fallback, and verify focus is not clipped by containers or hidden by rails/overlays. Focus not obscured is also a separate layout requirement. [S4](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

### F04 · P0 · Composite widgets have semantics without complete behavior

Source: [primitives.tsx](../packages/react/src/components/primitives.tsx).

- **Tabs:** selected tab gets `tabIndex=0`, others -1, but no arrow-key handler or activation callback exists. Browser ArrowRight leaves focus and selection on Account. IDs are derived from caller values without an instance prefix, so two groups can collide. The docs explicitly promise arrow navigation that does not happen. Implement activation, unique IDs, disabled handling and a defined automatic/manual activation policy. [S5](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)
- **Segmented:** buttons expose `role=radio` and click selection but no roving focus or arrow navigation; every option is a tab stop. Use native radios where suitable or implement the full radio-group contract, including form value/reset behavior. [S6](https://www.w3.org/WAI/ARIA/apg/patterns/radio/)
- **Menu:** `role=menu/menuitem` wrappers lack menu navigation, focus entry/return, dismissal and typeahead. Ordinary links should remain navigation, not pretend to be a menu. [S7](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/)
- **Dialog:** always announces `aria-modal=true` on a plain div, including inline previews. No focus containment, background inertness, dismissal or restoration is provided. Documentation suggests wrapping it in native dialog, which can create duplicate dialog semantics. Use one semantic owner, with content-only presentation separated from the modal primitive. [S8](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- **Tooltip/Popover:** surface wrappers only. Trigger relationships, opening/dismissal, placement, collision handling and focus policies belong to the missing behavior layer.
- **Toast:** status surface only. Queue, timed-dismissal policy, live-region lifecycle and action behavior are not provided.

**Recommendation:** build a small adapter proof using a mature accessible primitive layer before choosing a dependency. React Aria explicitly separates accessible interaction from presentation and supports composition; this fits Area's CSS ownership. Its presence would not remove Area's responsibility for labels, contrast, targets, or application integration. [S9](https://react-aria.adobe.com/customization), [S10](https://react-aria.adobe.com/quality)

### F05 · P1 · Motion-none does not mean no motion

[display.css](../packages/styles/src/components/display.css) hardcodes spinner 0.7s, skeleton 1.4s and indeterminate progress 1.1s. The explicit motion axis sets transition-duration tokens to zero but does not affect those animations. The browser confirms `area-spin` still runs at 0.7s inside `data-area-motion="none"`.

The OS reduced-motion query disables those animations, but axis transition overrides only apply to `:root:not([data-area-motion])`; an explicit root or child preset can bypass them. Decide and document preference precedence instead of accidentally deriving it from selector specificity.

**Next:** add motion-owned animation tokens or an explicit animation-enable mechanism; make none cover loops, entries, scrolling and transitions; provide an intentional override policy. Keep nonanimated loading/status information available. Test both OS preference and scoped presets.

### F06 · P0 · Package/API promises do not match the implementation boundary

- [tokens/package.json](../packages/tokens/package.json) exports a missing `src/index.ts`; a root import fails.
- [react/package.json](../packages/react/package.json) distributes TS/TSX source and calls build a no-op. This can be a deliberate workspace strategy, but a general npm installation needs a tested consumer/transpilation contract, declarations, exports and React peer policy.
- `ButtonTone` is `neutral`, while the manifest lists `primary`; Badge has the same mismatch. Neutral currently falls through to base styling, masking the contract difference. `classesFor()` silently drops unknown values.
- React Select allows xs/sm/md/lg while CSS/manifest has xl; Slider and Panel also expose narrower size unions than their manifest. Decide which are supported rather than assuming the helper guarantees parity.
- No tracked CI workflow or project license file was found. Clarify release intent, asset attribution, package contents, versioning and migration policy before distribution. This is a repository-readiness observation, not a legal conclusion.

**Next:** prove installation in a clean consumer outside this workspace. Derive or compile-check public props against the manifest. Give invalid variant inputs a detectable development failure. A private workspace kit may remain source-only, but then say so and test that route.

### F07 · P1 · Form and state ownership are incomplete

- Uncontrolled Slider derives `--_pct` once from `defaultValue`; native value changes do not update that fill. The docs inspector separately updates its own CSS percentage, hiding the library gap. Out-of-range values also need normalization consistent with the browser.
- Field prints a description/error and required asterisk but does not connect descriptions via IDs or convey required/invalid state to its control. `htmlFor` works only when the consumer wires an ID. Establish an explicit composition contract, not an implicit expectation that children infer it.
- NavItem's `disabled` sets ARIA/data attributes but leaves href/event behavior to the caller. CSS pointer suppression, if present, does not prevent keyboard activation.
- Progress clamps painted width but announces the raw value; zero/negative max and invalid values need a defined policy.
- Avatar's claimed required alt is optional in the type; broken-image fallback is not implemented.
- `CodeBlock.html` accepts raw HTML. Document trusted/sanitized input expectations; avoid presenting it as a safe arbitrary-string API.

**Done when:** controlled/uncontrolled values, reset, disabled behavior, label/help/error relationships, loading and invalid data all have consumer-facing examples and targeted tests.

### F08 · P1 · Tests prove less than the documentation claims

The registry validates light token ownership and values, but only checks dark maps for missing light keys. A cloned registry with an extra dark token outside its namespace and value `NaN` still reports **zero problems**; [measure.ts](research/2026-09-14/measure.ts) reproduces this without modifying production definitions.

The CSS parity script checks state selectors globally, rather than under the specific component. React props remain handwritten and loosely accepted by helpers. Docs rendering verifies static markup, not hydration or interaction. None of this invalidates the useful existing checks; it narrows their guarantees.

**Next:** extend integrity validation to all emitted maps, verify component-scoped state selectors, add public-prop contract checks, and add a small rendered interaction/composition suite. Run all checks in CI, with a clean-consumer install and browser smoke test. Use pairwise axis coverage plus targeted interactions and extremes, not an indiscriminate 50,688-screenshot matrix.

## The eight axes

### Theme · light / dark · highest priority

The palette resolution exists and resolved color themes are measured. The missing work is correct DOM inheritance, light reset, native color-scheme, portal propagation and system-preference handling. An explicit user setting should have a documented relationship to OS preference, storage and server rendering; prevent first-paint theme flashes.

**Completion:** F01/F02/F03 resolved; nested/native/portal tests pass. A higher-contrast mode is useful after this, but it needs a semantic policy rather than a second hardcoded palette.

### Neutral · neutral / cool / warm · sound range, composition unfinished

Three casts are enough for the first release. Preserve their ordinal ramp and measure semantic slots per cast. The 75/100/150 trial confirms identical rung numbers produce similar, but not identical, ratios. Extending the neutral catalog is lower value than correct nesting and stroke-role assignment.

**Next:** establish default control-identification and decorative policies; add surface/state visual comparisons for all three casts. Custom neutral temperature is feasible as a validated build-time preset, not an unconstrained runtime hue slider. **Completion:** all neutral selections work in scoped light/dark environments and meet the chosen role contracts.

### Accent/brand · 11 hues · expand validation before selection

The brand axis is technically `data-area-brand`; docs call it Accent. That is comprehensible if documented, but a public configuration should use one canonical key and one intentional display label. Indigo remains a reasonable default with info fixed to blue; red/green/yellow brand choices require real semantic collision review.

**Next:** fix hover text and focus contrast across all brands; confirm links, status colors and selection remain distinguishable without color alone. Status meanings should not change merely because a brand is selected. Allow a custom brand only through a generator that emits all roles and reports failing combinations.

**Completion:** full rendered brand-state matrix passes. Custom hue/chroma, secondary brand accents and data-visualization palettes are optional extensions; chart categories need their own semantics and non-color cues rather than reusing alert tones.

### Typography · Geist / compact / large / system · substantial work

Content type and density-controlled UI type are separated intentionally. However, font-family, body size and leading are applied to `body`; nested type-axis tokens do not automatically reapply those inherited CSS properties to an arbitrary subtree. Verify actual text, not only custom-property values.

**Next:** define a typography scope that consumes inherited font/role variables. Separate font-family choice from scale choice in future configuration without casually multiplying axes. Support consumer fonts, a fallback stack, font loading/self-hosting guidance, numeric formatting features, multilingual scripts and text enlargement. Density should continue to own UI type; document which text changes under each control.

Text-spacing and reflow checks should demonstrate that user adjustments do not clip labels, badges or controls. W3C's text-spacing criterion tests user overrides; it does not require those values as the design default. [S11](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html), [S12](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

**Completion:** scoped fonts work, fallback rendering is usable, enlarged text/long labels and supported scripts fit or wrap intentionally. Avoid adding more weight steps before these basics work.

### Density · compact / default · keep both, add target policy

Default medium is 32px/14px text; compact medium is 28px/13px. Compact xs is 20px/11px; glyph controls can be 12–16px. A glyph's visual size is not its interactive target size: surrounding labels can enlarge targets. Measure the actual clickable element and spacing.

WCAG 2.2's minimum target rule is 24×24 CSS px with defined exceptions, including spacing; it is not a universal demand for 44px boxes. [S13](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

**Next:** retain desktop compact mode, provide sufficient targets for icon-only and label-less controls, validate touch/coarse-pointer usage, and define a comfortable option only if target use cases require it. Do not silently enlarge every box and break the established outer-height rule.

**Completion:** actual hit areas, keyboard focus and spacing pass in documented configurations; size tiers align across mixed-component rows. Fix the density description that claims text holds while its emitted values actually change.

### Radius · 0 / 2 / 4 / 6 / 8 / 10 / 12 / pill · closest to complete

Flat radius, concentric subtraction, the 0.4 cap and shape-defining full radius form a coherent policy. Eight presets already provide ample choice. Some large presets necessarily converge on small controls; document that as geometry rather than promise every stop is visible everywhere.

**Next:** browser extremes for sharp and pill, compact xs, selected segmented inset, menu rows, panel flush edges and clipped focus. Ensure the radius visible after border thickness and inset matches the mathematical intent.

**Completion:** visual regression coverage for extremes plus mixed-size alignment. No further radius stops are recommended now.

### Surface · flat / outlined / raised / elevated · conceptual cleanup needed

This axis combines stroke width, elevation recipes and focus-ring geometry. These are related but not identical decisions. Elevated sets global border width to zero, while some separators and inset rings are fixed hairlines; “no strokes” is broader than the implementation. The audit's elevated outline button still has a shadow and a white fill, so the problem is inconsistent meaning, not automatic disappearance.

**Next:** define which semantic surfaces receive lift and which lines must survive; keep state/focus visibility independent of a decorative elevation choice. Compare cards, menus, inputs, selected segments and nested panels together in dark mode. Decide whether surface remains a small set of curated recipes or eventually separates boundary strength and elevation; do not add axes merely to expose every token.

**Completion:** each preset has a visible, documented purpose across the same component board, and none removes a required indicator. Typography and surface presets should not silently redefine accessibility thresholds.

### Motion · none / subtle / expressive · behavior unfinished

The preset vocabulary is sufficient. Durations and easing exist, but ongoing animation ignores the explicit axis and the override policy is inconsistent (F05).

**Next:** complete none first, then define entrance/exit/state/loading motion with purpose, interruption behavior and reduced-motion alternatives. An expressive preset should communicate hierarchy, not just make everything slower.

**Completion:** OS and explicit preferences agree with documented precedence, including nested scopes; loading remains understandable without movement; animation tokens have no unowned duration literals.

## Further theming and customization

### Useful now: curated profiles built from existing axes

Introduce named, serializable recipes such as a dense editor, a quiet settings application and a more spacious content interface. Each recipe selects existing axes; it should not fork component CSS. Store a schema version, validate values, provide reset/export/import, and distinguish shipped profiles from custom/unverified ones. Build the first profiles using real product screens, not just swatches.

A scoped theme wrapper is a useful public abstraction; established systems such as Radix Themes expose theme configuration as an explicit wrapper. Area's implementation still needs its own verified inheritance and portal behavior. [S14](https://www.radix-ui.com/themes/docs/theme/overview)

### Next: validated custom presets

Allow consumers to define a font family, brand ramp, neutral cast, spacing/density recipe, radius recipe or elevation recipe through a documented schema. The compiler should verify namespace ownership, token completeness, finite values, dimensions, contrast and derived relationships. Report invalid combinations with actionable errors. Keep raw CSS overrides available as an escape hatch, clearly outside the shipped preset guarantee.

A preview/export tool should show more than the attractive result: display actual text/control/focus checks, scope inheritance and affected components. Save values and schema versions, not only screenshots. Do not claim arbitrary custom colors inherit the guarantees of the 66 shipped themes.

### Contrast and preference policy

A high-contrast profile is valuable, especially given the user's preference for soft default chrome. It should strengthen required component indicators, focus and text while letting decorative edges remain quieter. Forced colors should use platform/system colors and be tested separately. An optional high-contrast profile is not a substitute for establishing an acceptable default contract.

If adding a contrast axis would write tokens already owned by neutral/brand/theme, that breaks Area's invariant. First choose an ownership model: for example, a contrast profile can supply separate policy inputs that semantic resolution consumes. This is architecture work before another inspector toggle.

### Interchange and design tooling

Current `tokens.json` is an Area-specific schema of string values and metadata, not DTCG token interchange. Add a separate exporter rather than replacing the docs' input format prematurely. The DTCG 2025.10 Format module defines typed tokens, aliases and metadata; its stable community specification is intended for implementation, but is explicitly not a W3C Standard. [S15](https://www.designtokens.org/tr/2025.10/format/)

Its Resolver module describes conditional contexts and resolution order, a useful conceptual match for Area's axes. Prototype mappings for theme/brand/neutral before promising portable behavior for CSS calculations or browser-specific effects. Validate exported and resolved values against Area's own output. [S16](https://www.designtokens.org/tr/2025.10/resolver/)

A Figma library could consume validated exports later. Do not revive the archived destructive sync scripts or rename historical provenance into active tooling. Any future sync needs stable identifiers, a diff, and reversible updates.

### Defer until real demand

Additional accent families, arbitrary per-component radius knobs, independent typography weights, glass/blur, global transparency, more motion presets, and a second neutral semantic tone would increase maintenance before solving current reliability. Data visualization, date/time controls, rich text and mobile-specific patterns should each have a defined product need and separate acceptance criteria.

## Visual refinements

These are design recommendations rather than verified defects unless a finding above says otherwise.

1. **Judge strokes as a hierarchy of jobs.** Keep large framing quiet. Give editable fields, selected states and focus enough definition for their role. Compare flat and dark surfaces so shadow does not conceal weak borders.
2. **Separate selected from focused.** Selected segment, selected chip, active nav and keyboard focus need distinct signals that can coexist. Validate with grayscale and forced-color checks; add a checkmark/shape when color is the only cue.
3. **Reduce the jump on hover.** New quiet rest strokes still jump to existing stronger hover tokens. Review resting, hover, pressed, selected, invalid and focus side-by-side. Keep label color stable while choosing readable fills.
4. **Refine surface relationships before adding decoration.** Review modal over scrim, menu over panel, selected segment in track, card on subtle ground, and nested code/preview. Tune border, fill and shadow together; avoid stacked frames with identical emphasis.
5. **Prove shared metrics with a mixed row.** Button, Select, Input, Segmented and Chip at one tier should have aligned outer boxes, labels and icon centers at both densities. The native Select arrow and platform font are useful stress cases.
6. **Test real content pressure.** Long translated labels, counters, validation text, multiline descriptions, empty values and narrow inspector widths reveal more than centered single-word demos.
7. **Keep token badges legible.** Uniform badge size is a good rule; check long token wrapping, swatch outline over pale fills and vertical alignment in prose. Avoid solving a long name by shrinking text below the caption scale.
8. **Calibrate visual emphasis with application compositions.** Build settings/form, table/filter/empty-state, and command/menu/dialog flows. This will reveal whether the same semantics hold beyond the current documentation layout.
9. **Make documentation reflect behavior.** The current installation example implies normal package consumption; Tabs promises behavior it lacks. Show component maturity and distinguish a static surface demo from a working interaction.
10. **Preserve provenance, remove stale claims.** Keep Area as the current identity. Old project names belong in the archive. Literal upstream icon names are not aliases. Source comments still contain stale axis counts, old radius names, old ownership descriptions and unsupported blanket comparisons to other products; replace claims with dated evidence or scoped rationale.

## Component completion

First finish the existing 36 manifest components rather than treating page count as coverage:

- **Native inputs and actions:** Button, Input, Select, Textarea, Checkbox, Radio, Switch, Slider, Chip. Complete form relationships, controlled/uncontrolled state, loading, focus, target size and reset behavior.
- **Composite interaction:** Tabs, Segmented, Menu, Dialog, Popover, Tooltip, Toast. Deliver or explicitly delegate behavior through a supported adapter, with keyboard and assistive-technology examples.
- **Presentation and structure:** Field, Panel, Card, Table, Nav, Separator, Badge, Avatar, Alert, Progress, Skeleton, Spinner, Code/CodeBlock, Token, Kbd and related manifest entries. Verify semantics, content resilience, states and theme extremes. A visual Table does not imply sorting, selection or a data-grid engine.

Then prioritize additions by product need:

1. **Combobox** for searchable selection, including input/list relationship, keyboard behavior, loading, empty/error states and async results. Keep native Select for simple finite choices. WAI-ARIA defines several combobox variants, including select-only; Area can deliberately reserve its own Combobox name for editable search, but should not claim the broader term always requires text entry. [S17](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)
2. **Disclosure/Accordion** and **Breadcrumb/Pagination** when actual information architecture needs them.
3. **Search/filter patterns, empty/error states and form validation patterns** assembled from existing components.
4. **Date picker, tree, command palette, virtualized list and data grid** only with a supported behavior foundation and concrete use cases. They are separate interaction projects, not just more CSS variants.

## Research and sources

All sources below were consulted on 2026-09-14. W3C Understanding/APG documents explain requirements and implementation patterns; the normative WCAG standard remains [WCAG 2.2](https://www.w3.org/TR/WCAG22/). Recommendations above are Area-specific synthesis. No external library was installed or adopted by this audit.

- **S1:** W3C, [Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) — role-dependent component identification and state contrast.
- **S2:** W3C, [Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) — normal text, placeholders and hover text.
